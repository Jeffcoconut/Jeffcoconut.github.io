# mini_skyvern 调试与修复流程复盘

整个 调试+Debug 周期流程是：
**草稿版 → 依prompt对抗（R1–R5）→ 架构重构（四条新需求）→
A 队验收 → 专家团第三方审查 → 用户反馈 → 三轮 debug 对抗（d/e/f）**

>现在在不少论文当中其实会注意到 agent 之间存在比较严重的为了讨好人类而进行的妥协行为。所以在一开始设置目标节点 prompt 的时候，严格限制了 **A 队不能相信 B 队口供且仅向人类负责** 并且要求 A 队对于任何宣称已经修复的问题提供 **以下三类证据之一：真机 run 的数据库记录、零模型消耗的取证脚本、截图人工核对。**。不知道这两条死命令在整个生成调整的过程当中起到多大的作用，但是最终结果相对令人满意。
{: .prompt-tip}

## 一、项目中的报错类型及案例

### 1.1 静默腐化：错误被吞掉，系统带着病继续跑

**案例 1 · schema 缺列（R1，A1-2，致命）**

- 现象：任务失败，界面上只有一个 `failed`，无任何原因。
- 取证：直接查库写错误原因，抛 `sqlite3.OperationalError: no such column:
  error_message`——而这一列在 schema 文件里**写了很久**。
- 根因：`CREATE TABLE IF NOT EXISTS` 对已存在的旧表完全不生效。开发库是
  新建的所以一切正常，用户的老库永远缺列；每次写错误原因都抛异常，被上层
  `except` 吞掉。**错误处理链路本身在静默失败**，于是用户永远看不到错误原因。
- 修复：`_MIGRATIONS` 登记制（加列必须登记，启动自动 `ALTER TABLE` 补列）+
  `_assert_schema_matches_models` 启动自检（模型有而表里没有的列大声打印）。
- 教训：**任何「写入后读不到」的链路，都要假设写入可能一直在失败**。schema
  演进必须有显式迁移机制，`IF NOT EXISTS` 不是迁移。

**同类案例**：

- A1-3：兜底 `except` 不传 error_message，二次掩埋——错误处理代码自己也要被测试。
- 验收期 `class UploadedQuest: quest_id = quest_id` NameError：上传/目录装载
  两条接口**从未跑通过**，但界面只提示「装载失败」，看着像目录填错了。
- notes 同一句话重复两遍：看着像执行了两次，被当成正常日志放过。

### 1.2 静默的错误成功：状态是 completed，数据是错的

**案例 2 · 跨页提取丢失（R2，A2-1/A2-2，致命）**

- 现象：books.toscrape 翻两页提取 40 本书，结果 20 条全是第 2 页，状态却
  `completed`。
- 根因：提取只在循环结束后对**末页**做一次。第 1 页数据在翻页那一刻就永久
  丢失，而系统没有任何机制知道「曾经存在过一个第 1 页」。
- 修复：提取时机改为「离开页面前必提取」（每步动作执行前提取当前页）+
  `ExtractionAccumulator` 跨页累积 + 失败出口 `_fail` 统一化（超步数/abort/
  terminate 四条失败路径都先落盘已累积数据并标注「部分」）。
- 教训：**「成功」必须定义在数据上，而不是流程走完了**。凡是流水线型 agent，
  问自己一句：中间产物在哪个时刻被持久化？如果答案是「最后一步」，你就有一
  个 A2-1。

**案例 3 · 缓存回放丢中间页（R5，A2-7）——同一根因的第二次出现**

- 现象：同一任务第二次跑（命中缓存走脚本回放）结果比第一次更差：只有末页数据。
- 根因：回放路径 `_run_with_code` 绕过了 Agent 主循环，也绕过了「离开页面前
  必提取」——钩子只挂在末页。
- 修复：脚本生成器在**起始 goto 后、每个翻页动作后、结尾**各注入
  `await _extract_page(page)`；旧脚本不引用钩子则 no-op 无害，向后兼容。
- 踩坑细节：首版只在「翻页后」注入，实测回放仍丢第 1 页——**起始落地页没有
  钩子**。补上才修对。
- 教训：**修一个 bug 时，把「数据流经的所有路径」列成清单逐条核**。Agent 路径
  和回放路径是两条路径，只修一条等于修了一半。这个「列路径清单」的动作，
  后来在 popup 问题（案例 5）里又救了一次。

### 1.3 数字在说谎：指标本身是错的，而且长得很合理

**案例 4 · token 虚高 11.4 倍（R3，A2-6）**

- 现象：日志报单次决策 103659/128000 token，额度烧得飞快。
- 取证：跟着钱走（见案例 7）的同时拆开 prompt 各部分估算，发现真凶不是元素
  列表，而是 **base64 图片被当文本估算**：`len(json.dumps(messages))//4` 把
  一张约 160KB 的 jpeg 算成约 22843 个「token」——图片 base64 的字符数根本
  不是它的 token 成本（视觉模型按分辨率档位计费）。
- 修复：`count_message_tokens` 分离文本/图片（图片按 detail 档位固定 85/1500
  token）；硬顶强制只看文本 token。顺带发现旧「最后安全网」因三重缺陷完全不
  生效——**不生效的保险丝比没有保险丝更危险**，因为它让你以为有保护。
- 教训：**任何估算公式，都要问「这个数是谁的成本、按什么口径」**。把字节数
  当 token、把旧长度当分母（案例 6）、把 39.7% 卡在 40% 阈值下（案例 5 的
  40% 线），本质都是「口径与被度量对象错位」。

**案例 5 · ratio 口径两次返修（验收期）**

- 第一版：页面元素数量一变就直接「变化 100%」——格子数不等时直接返回 1.0。
- 第二版：文本长度差用**旧长度**作分母，内容翻一倍 ratio 饱和到 100%，于是
  「展开一张 5 行表格」和「整页换掉」在界面上是同一个数。
- 终版（当前代码）：格子差按 `max(len)` 归一，文本差用 `max(两者)` 作分母，
  两项取 max。展开表格显示 0.751，整页换掉才是 1.0。
- 教训：**给人看的连续量，不能当结构变化的布尔量用**。界面上的每一个数字，
  都要能回答「用户拿它区分哪两种情况」；回答不上来，这个数就是在说谎。

### 1.4 引用与状态失同步：代码里有两个「当前页面」

这是你最近三轮反馈（d/e/f）的主线，也是 agent 项目里最隐蔽的一类：**多个
组件各自持有对同一外部状态的引用，切换发生时只更新了一处**。

**案例 6 · popup 不切换 → final_url → adopt_page（e 轮 + f 轮，三连根因）**

- 第一层（e 轮）：click 百度结果链接（`target="_blank"`）成功，但主循环的
  `page` 不切换——C4 多标签逻辑只覆盖 new_tab/switch_tab 动作，不覆盖
  click 弹出的 popup。修复：`_click` 前后对比存活页集合找出新标签
  （`_adopt_popup`），并入同一条 `_resolve_active_page` 切换通道——**不写第
  二套逻辑**。
- 第二层（e 轮附带）：切换后 `block_runner` 手里还是旧 page 引用，`page.url`
  读到的仍是起始页，传给下一块 inherit 的还是百度 URL。修复：Agent 三条出口
  返回 `final_url`，`next_url` 优先读它。
- 第三层（f 轮，你的四块流程暴露）：前两步进了东财，第三四步却退回百度搜
  茅台。根因：`BrowserManager.get_page()` 永远返回启动时的 `self.page`；
  Agent 切换新标签只更新了主循环**局部变量**，`browser.page` 仍是百度旧标签，
  下一个块开头 `get_page()` 拿到的就是旧页。修复：新增 `adopt_page()`，谁
  切换了 page 谁负责同步；`get_page` 语义不动，改一处惠及 custom/automation
  两条路径的全部调用点。
- 教训：**「状态切换」类 bug 会以递进方式暴露**——每修一层，下一层引用失同步
  才浮出来。防御动作是：项目里所有「当前页面/当前会话/当前用户」的引用持有
  者列一张表，每次切换事件发生时，逐行问「这一处更新了吗」。f 轮的修复之所以
  干净，是因为最终选择了「单一写入口」（adopt_page）而不是在每个调用点打补丁。

**同类小案例**：帧步号「永远停在第 1 步」。`step_order` 是块内步号、跨块重置，
帧记录没有块归属，前端只渲染「第 N 步」——四块各跑一步时看起来就是停在 1。
这不是 bug 在说谎，是**数据结构缺少归属维度**。修复走全链路：模型 → schema →
迁移登记 → repo → publisher → engine → 前端标签「块 N·标题 第 M 步」，老数据
回退旧标签。教训：加一个展示维度时，沿「产生 → 存储 → 传输 → 渲染」整条链
核一遍，漏任何一环都是半截修复。

### 1.5 挂起与超时：系统不是错了，是停了

- **LLM 无超时**（R3）：旧版 `AsyncOpenAI` 不显式给 timeout，供应商挂起 →
  整个任务永久卡死，且 LLM 异常会冒泡越过 `_fail` 的数据抢救，已累积数据白丢。
  修复：`timeout=120s + max_retries=2`；决策/校验加 try/except，决策失败转
  `_fail`（保数据），校验失败降级为「继续」。
- **导航 135s**（R4）：三档 goto 各跑满 30/45/60s，不可达主机要卡三分钟。
  修复：commit 探针（只等响应头，20s 快速失败）+ 尽力等 DOM 就绪。实测 21s
  干净失败。
- 教训：**agent 系统的每一个外部依赖（模型、网络、浏览器）都必须有「挂起
  预算」**。没有超时的外部调用不是慢，是定时炸弹；而且炸弹爆炸时往往先炸掉
  你的数据抢救逻辑（异常路径越过兜底）。写代码时问：这个 await 如果永远不
  返回，我的任务会怎样？

### 1.6 配置与钱：跟着钱走（R3-C，全周期最高价值发现之一）

- 现象：用户充值后余额一动不动。
- 取证：A 队「跟着钱走」，直连两家供应商的账户接口。发现 `.env` 同配了
  SiliconFlow 与 DeepSeek 两套 key，`MODEL_ROUTE=multimodal` 只调用
  SiliconFlow，而用户的钱在 DeepSeek——**钱和被调用的模型不在同一条路由上**。
- 修复：切路由 + 新增启动自检 `account_balance.py`：**把当前路由实际会花钱的
  账户余额直接打印**，余额为 0 告警。
- 教训：**多配置源系统里，「配置 A 生效、配置 B 付钱」这类错配只有跟着资源
  消耗走才能发现**。日志、余额、token 计数都是「钱」的形态。这个自检若早存
  在，错配第一秒就会被发现——把资源消耗做成启动时的可见输出，是便宜且高回报
  的工程动作。

同族运维陷阱两条，留作警醒：`pkill -f`/`pgrep -f` 会匹配到执行命令的 shell
自身（用括号正则 `uvicorn[ ]api.server` 规避）；Python 默认 stdout 块缓冲会
吞掉后台服务日志，取证前先 `PYTHONUNBUFFERED=1`——**观测设施坏了的时候，
你会把「看不到日志」误诊成「没有日志」**。

## 二、对抗过程本身的价值：A 队揪出的「不彻底修复」

B 队的首轮修复两次被 A 队发现不彻底，这两个故事比缺陷本身更值得记住：

1. **40% 线卡线漏网（d 轮）**：首轮修复用「占视口 40% 以上剔除」拦布局容器，
   百度 `#content_left` 带 `tabindex="0"` 被判可交互，视口裁剪后占 **39.7%**，
   卡在阈值线下漏网。A 队复测截图里那个竖长大框就是它。补齐：collect 剔除
   阈值独立收紧到 25%（剔除与分组用不同阈值，因为职责不同）+ 超大组自适应
   减半拆分。
2. **verify 侧绕过怀疑性重试（d 轮）**：怀疑性重试原只挂在决策分支，而某次
   完成路径是「click 成功 → verify_completion 判 complete」——校验通道没有闸。
   补齐：verify 侧在「早期预算 + 本步无成功动作」时同样驳回一次；「动作成功 →
   verify 确认」的正常流程不受影响（**防御不能扰民**，否则用户会关掉防御）。

方法论提炼：**阈值类修复必须用「卡线样本」验收**（39.7% 对 40%）；**防御性
逻辑要挂在所有能到达同一结论的通道上**（决策说 complete 和 verify 说 complete
是两条通道）。验收时主动构造「刚好压在阈值两边」的样本，比跑十个正常样本有用。

## 三、取证动作清单（带走去下一个项目）

把上面的案例压成动作清单：

1. **不信口供机制**：真机 run 的库内记录、零模型取证脚本、截图人工核对；
   界面结论必须有后端旁证（A 队纯界面验收累计漏报 5 处静默缺陷，全部是核
   后端数据时发现的）。
2. **token预算控制细节**：余额、token 计数、调用量，任取其一做启动可见输出。
3. **列路径清单**：数据/状态流经的每条代码路径（Agent/回放、决策/verify、
   上传/目录装载）逐条核，修一条不算修。
4. **列引用持有者表**：所有「当前页面/会话」引用持有者，切换事件逐行核更新。
5. **口径审问**：界面上每个数字回答「用户拿它区分哪两种情况」；每个估算公式
   回答「这是谁的成本、什么口径」。
6. **卡线样本**：阈值修复必须构造阈值两侧样本验收。
7. **挂起预算**：每个外部 await 问「永远不返回会怎样」；异常路径不得越过数据
   抢救兜底。
8. **静默降级专项检查**：「不报错、只是少做了事」是最贵的缺陷类——回放 0 帧、
   视觉缺失、截断不回报都属此类。修复时给降级打**可见标记**（「未走 Agent
   决策」「字段未经模型清洗」「视觉输入不可用」），让少做的事永远摆在台面上。
9. **回归沉淀**：每轮验收标准固化成零外部依赖的断言脚本；修新缺陷前先跑旧
   断言，防止旋转门。
10. **作用域纪律**：修复限定授权文件清单；确需扩张时（如 e 轮动到
    block_runner 的 1 个字段）单独声明理由与最小性，不偷偷扩。

## 四、回到你的目标：怎样提出更高质量的 prompt

这整轮周期里，**你的几次反馈恰好命中了自动化验收漏掉的东西**，值得总结成
习惯：

- 你给的不是「这里坏了」，而是**可复现的完整流程 + 预期与实际的差异**
  （「前两步顺利、第三四步退回百度」）——这直接省掉了取证的第一步；
- 你区分了「主标准未达成」与「观感问题」（边框消失、整页转变的误判观感），
  让修复能分层排优先级；
- 你在 R4 提出「付费 API 无响应 → 免费端口 → 纯自动化提取」的降级思路，被
  落地为三层降级链——**好的 prompt 是给约束和兜底语义，不是给实现细节**，
  A/B 队据此自行修正了「降级只能在同类工作端点间做」的认知。

反过来，本周期也暴露了 prompt 的两类失败模式，供你自省：其一，**目标描述
宽松会被模型字面满足**（「输入茅台并搜索」被满足为「输入了茅台」，没按回车
也宣布完成）——对关键动作写验收式描述（「输入后按回车，且 URL 变为搜索
结果页」）；其二，**警告若误报会训练用户忽略所有警告**（R1 中意图体检曾把
「提取前 5 条搜索结果」误判为夹带操作）——防御性提示的精度比覆盖率重要。

最后一句话总结这份复盘：这个项目的质量不是某一次聪明修复换来的，而是
**「静默缺陷必须可见、数字必须可审问、路径必须列清单、回归必须零依赖」**
这四条纪律反复执行的结果。纪律可以原样带到你的下一个 agent 项目。
