## part0 总览:

本次项目采用的是非常经典的RAG框架：使用**WordprocessingML**对原生word文档进行解析，然后根据章节等属性做了简单的**元数据增强 + 父子块结构**（提升检索精准度并保证输出内容完整性）。接着在具体检索层面，采用了传统的**FAISS(dense) + BM25(sparse)**算相似度，归一化后加权融合最终选出k个候选内容块。随后通过**Reranker 大模型**进行精排，并加入**MMR**来保证内容的多样性。最后进行上下文组装，在不超过token预算的前提下添加标记并输出最终文档。

本次项目调用了以下大模型接口：
1. deepseek-v4-flash ( LLM问答 用于DEEP_AGENT部分 )
2. Qwen3-Reranker-4B （Reranker模型）
3. BGE 本地部署模型 （Embedding 模型）

### 2.2 WordprocessingML

前置转化word采用的**核心方法**是用 `lxml.iterparse` 流式解析 `document.xml`，然后按 Word 分页标记切分文本。而解析完以后的文档中有大量的分页符 *(决定了召回页码的准确性)*，所以要进行页码**去重** ：硬分页 *(主动插入分页)* 后紧跟的软分页 *（自动分页）* 视为同一页界的重复标记，防止页数混乱。

```
document.xml
    │
    ├── <w:t> 文本 run               → 累积到当前段落
    ├── <w:tab>                      → 转为制表符
    ├── <w:br type="page"/>          → 硬分页 → 翻页
    ├── <w:lastRenderedPageBreak/>   → 软分页 → 翻页
    ├── <w:tbl>                      → 标记本页 has_table=True
    └── <w:p> 段落结束                → 写入一行
```


>**优势**：本案例当中采用`lxml.iterparse`的优势有两点。
> 1.word情况下比 LibreOffice 转 PDF 再 ocr 处理准确性更高。
> 2.流式解析 的同时进行 `elem.clear()` 及时释放，避免 XML 全量建树的内存峰值。

### 3.3 处理标准

在本次尝试中，我们总共进行了以下标准处理：

1.**章节栈维护**：
  在遇到一级标题时 → 清空栈，压入一级  *(新法律文件开始)* ;

  在遇到三级标题时 → 栈截断到二级，压入三级 ;

  eg:
  每个段落携带的 `section_chain` 就是当前的章节链，例如：
  ```json

  ```

2.**跨页段落合并**：当上一页最后一段"未以句末标点结尾"（`。：；` 等），且下一页首段不是标题、也不以新条目编号（`第X条`/`一、`/`1.` 等）开头时，判定为同一段落被分页截断，合并成一个文本块。 *（优先保证同一文本块不被拆分）*

3.**Token 计数**：统一使用 `tiktoken` 的 `cl100k_base` 编码（GPT-3.5/4 所用）。

4.**目录页污染**：比如第 1 页为目录页，目录行以"制表符+页码数字"结尾（`《信托法》\t25`），此类行一律不认定为标题。

## part4 Parent-Child Chunking

### 4.1 总览

>拿到了已经切好且做好信息增强的chunk以后，进行RAG检索仍然存在挑战。因为 -- 如果要保证整体检索的准确性，则文本块越小越好（ *embedding语义更加精确简洁*）；如果要保证回答问题的质量，则对文本块的内容量有一定要求（ *足够的上下文长度建立一个文本情境*）。所以，在本项目中通过**Parent-Child Chunking**嵌套的方式进行文本预处理：这样既可以检索子块，保证检索精度；也能够在LLM要分析的时候，从子块反调用父块，使大模型获得尽可能完整的上下文。除此之外，项目在实操过程中还进行窗口扩展，从而控制token预算。
{: .prompt-info}

![XML RAG 架构图](/assets/img/xml_RAG1.png){: width="80%" }

>- **父块（Parent）**：800~1200 tokens 的语义完整块，用作上下文窗口
>- **子块（Child）**：~250 tokens 的精细块，用作检索单元

### 4.2 算法实现

![XML RAG 架构图](/assets/img/xml_RAG2.png){: width="100%" }

Parent-Child Chunking除了父子嵌套结构外，还有一个核心处理是设计了一个子块间的滑动窗口，通过语义重叠的方式防止子块间因为硬截断导致信息损失。

在父块层面，Parent-Child Chunking 在切父块的时候以一级标题为强制边界，二级标题在当前父块达 500 tokens 时则可以切分；父块目标区间为 **800–1200 tokens**，硬上限 1200，若单段独立超出则整段成块且不内拆。构建后，对不足 500 tokens 的短父块，在同一法律文件内优先向前合并，合并后不超上限。

进一步在父块内进行处理，Parent-Child Chunking 首先对原始父块文本进行预处理，依据 。**！？；\n**等强分隔符进行切分，并将相邻的右引号、括号粘连至前一句，得到带有完整语义边界的句子序列 S=[s1,s2,...,sN]。这样至少能够保证最小单位的语义完整性。

然后，从起始位置 start 出发，算法按语句顺序不断向子块当中添加token，直至加入下一句会超过子块文本长度**250token**上限时，在当前句处切断，形成一个子块。此外，算法还设置了一个尾部保护阈值(*60 token*)：若当前窗口之后剩余的所有句子总 token 数不足 60，则直接将剩余部分全部合并至当前窗口，从而避免产生零散的文本碎片。

接着，为保证相邻子块间的上下文连贯性，算法在确定当前窗口的结束句后，下一个子块的起点将从上一个子块的结束句向前推50token开始，并重复前述的操作。这一机制确保了相邻子块之间共享约**50 token**的文本片段，充当了窗口间的“语义锚点”。

通过上述方法，算法在计算效率（*严格控制输入长度*）与语义完整性（*句子边界+跨窗重叠*）之间取得了有效平衡，保证了检索的有效性和长文本推理的回答能力。

### 5.2 嵌入后端 到 FAISS 和 BM25

在后端嵌入的部分，模型使用了本地部署的BGE模型。在实现过程中，AI进行了统一接口设计，并将所有文档进行了L2归一化处理。（**使内积等于余弦相似度**）

```python
class EmbeddingBackend:
  """统一的文本嵌入接口"""

  def encode_docs(self, texts: list[str]) -> np.ndarray:
    """L2归一化"""

  def encode_query(self, text: str) -> np.ndarray:
    """对于BGE系列模型而言 查询侧增加检索指令前缀能够提升检索效果"""

```

除此之外，在后续复盘的过程当中，我们还注意到：
>AI还优化了指令前缀相关内容，经查验在BGE模型的原始论文中提到查询侧加指令前缀可提升1.4%的检索效果，但并不是在所有场景下都有效。

```python
QUERY_INSTRUCTION = "为这个句子生成表示以用于检索相关文章："

def encode_query(self, text: str) -> np.ndarray:
  if self.backend == "local" :
    q = QUERY_INSTRUCTION + text
    vec = self.model.encode([q], normalize_embeddings=True)
    return vec[0]
```
通过以上操作，我们将预处理完的文本块转化成了具体的向量。

有了BGE模型构造好的向量后，我们引入**FAISS IndexFlatIP**进行暴力搜索,重点在筛选出语义上与检索向量相近的子块。(FAISS Library下的函数，可以大幅提高向量内积的计算速度；反之，用BGE的向量然后叠加numpy在数据量大的情况下计算非常满。在已经L2处理的背景下只需要求内积即可得出相似度)

具体代码如下：
```python
faiss_index = faiss.IndexFlatIP(dim)  #内积索引
faiss_index.add(embeddings)           #(N, dim)
```

>关于FAISS用到的PQ矩阵优化算法（以及BM25和一些相关nlp的topic）等内容将会单独写几篇文章来进行分享。

除了**FAISS IndexFlatIP**进行语义上的检索匹配以外，项目还引入了**BM25**一同构建向量索引。

>单纯的语义检索相似性存在一定的局限性，比如说对于NASA等特殊专有名词，通过FAISS很难直接捕捉到，所以需要通过BM25通过词语对应的角度进行弥补。当然，BM25这样从词汇出发进行检索的方式也有问题，比如很难分辨“苹果”，到底是在说苹果公司还是苹果这一种水果。这也是为什么我们需要在后续引入混合检索。
{: .prompt-tip}

BM25的核心思想就是：一个词如果越稀有、在某文档中出现的越频繁，则该词对区分该文档的贡献越大。（通过IDF 和 TF的表达优化解决这一问题，处理完后再进行归一化消除文章长短的影响）

同时，搭配上搜索引擎模式（cut_for_search）来适当的放宽BM25检索词精准性的约束，增加检索的鲁棒性。
>eg: “私募基金” 可以同时对应上 “私募” “基金” 以及 “私募投资基金”等，让整体的词语对应覆盖率提升

```python
corpus_tokens = [tokenize_zh(text) for text in child_texts]
bm25 = BM25Okapi(corpus_tokens)
```

### 5.3 检索实现

>在拿到了经过FAISS和BM25构建好的向量索引后，我们将筛选那些与检索向量最为匹配的文本块。首先，将FAISS和BM25的结果按照0.5的权重进行混合加权粗排，并选出top 20的文本块。然后，对top 20的文本块进行精排，最后再通过MMR补齐信息的维度，确保最终提交给LLM处理的文本内容尽可能全面。
{: .prompt-info}

#### 5.3.1 混合检索


**首先进行混合检索。**

由于余弦相似度的值域是[-1,1], BM25打分的值域是[0,∞),公式中加权前还要进行归一化处理。

具体的公式如下所示：


$$\text{final\_score} = \alpha \times \text{minmax\_norm}(\text{dense}) + (1-\alpha) \times \text{minmax\_norm}(\text{sparse})$$


其中：
- **dense_scores**: 查询向量与全量子块的余弦相似度（FAISS 内积）
- **sparse_scores**: BM25 打分
- **minmax_norm**: 归一化到 [0,1]，消除量纲差异
- **α**: 权重系数（ 两路均衡的0.5是一个比较个人经验化的权重，可以根据个人需求进行调参优化 ）

#### 5.3.2 精排

**拿到top-20的粗排序结果后，再用Reranker模型进行精排。**

在本项目中，因为总体的文本量较小，且粗筛后的文本token量也可控，所以精排时采用精度更高，但是速度更慢的Cross-Encoder架构的Reranker模型。

在Cross-Encoder当中，查询和子块都拼接在一起，作为一个整体输入模型。然后模型内部的Self-Attention层让查询的每个词和子块的每个词相互交互，最终输出一个单一分数，表示这对(query，passage)的相关程度。

如果用数学公式表示如下图所示：


$$\text{score} = \sigma(\text{CrossEncoder}([CLS]\ \text{query}\ [SEP]\ \text{passage}\ [SEP]))$$


其中：
- **[CLS]（Classification Token）**: 放在开头，它的最终隐藏状态会被视为整个输入对的“聚合表征”，用于后续的分类或打分。
- **[SEP]（Separator Token）**: 用于明确告诉模型，“查询”和“段落”是两个独立的句子，模型会对它们进行区分。
- **关键点**: 它将查询和段落拼接成一条完整的序列，一次性喂给模型。这意味着，模型从第一层注意力机制开始，就能让查询中的每一个词直接“看到”段落中的每一个词。
- *好 AI介绍的非常清晰 直接复制*

> 在nlp论文阅读总结的文章中会详细介绍BERT类模型，有一定的里程碑性质。当然，还有许许多多其他类别的模型。

得到精排的名次后，我们将先保底抽取top 3个文本块，确保后续LLM模型能收到的文本量是充足的。然后从第4名开始，只有分数大于等于threshold的才能继续被选中，直到选取的子块个数达到最大值5个。

>通过这样的设置，确保能选出足够的文本来供LLM回答问题，同时上限和threshold的设置则避免了过多不够相关的片段被选中，影响整体的回答质量。
{: .prompt-tip}

#### 5.3.3 MMR多样性补充

**最后，再从剩余子块池中选取不超过两个相关性相对较低的文本子块作为补充。**
MMR(Maximal Marginal Relevance)顾名思义，即从精排未选中的剩余候选池中，选取“相关但是不冗余”的补充子块，提升选取文本块内容的覆盖面。

具体的公式如下所示：


$$\text{mmr\_score} = \lambda \times \cos(\text{query}, \text{candidate}) - (1-\lambda) \times \max_{s \in \text{selected}} \cos(\text{candidate}, s)$$


其中：
- **λ**：相关性权重（默认 0.7，偏向检索相关性，保守一些）
- **cos(query, candidate)**：候选与查询的相似度
- **max_cos(candidate, selected)**：候选与已选集合的最大相似度（冗余度惩罚）


>因为精排可能选出多个高度相似的片段（同一法条的不同子块）。所以通过引入 MMR 的方式，来惩罚冗余度，补充多样性视角。

### 5.4 上下文组装

在检索增强生成的最终组装阶段，我们需要将精排与 MMR 选中的子块重新映射回原始父块，组装成 LLM 可直接处理的上下文。核心设计目标包括以下几点：
- 每个片段都必须带来源标记（法律名称、章节、页码）
- 总 token 数控制在 3500 以内，截断处保证句子边界完整
- 让精排分数更高的来源获得更多输出权重

为此，我们按父块分组，将每个父块下所有子块的 rerank_score 求和作为该块的权重（MMR 补充块无分数时按 0.5 计），然后按权重比例分配总 token。

分配好输出权重后，以各子块在父块中的位置为中心，按句子为单位向左右两侧交替扩展，直到逼近该块所分配的 token 数，同时保证每次截断都在完整句子处结束。扩展完成后，为每个片段添加【来源：章节链，第X-Y页】的标记。接着进行全局预算校验，若超出 3500 则触发缩窗重试。由此，既按相关性合理分配上下文长度，又保留来源可追溯性，让 LLM 在回答时“有据可依”从而减少幻觉的产生。

最终，我们拿到如下图所示的文本块。

**返回结构**：
```python
{
    "context_text": "...(带来源标记的完整上下文)...",
    "source_info": [
        {
            "parent_id": "parent_0042",
            "section_chain": ["《证券投资基金法》", "第二章 基金管理人"],
            "page_range": [5, 8],
            "snippet_preview": "第十二条 基金管理人由..."
        }
    ],
    "total_tokens": 3200
}
```

## 6. DeepAgent 问答框架接入

### 6.1 整体架构

```
用户 ←→ Web 对话界面 (index.html)
              │
              ▼
         agent_server.py (FastAPI, 端口 8900)
              │
              │  POST /chat { message, thread_id }
              ▼
         deepagent_app.py (Agent 核心)
              │
              ├── LangChain create_agent
              │     ├── LLM: ChatOpenAI (DeepSeek)
              │     ├── Checkpointer: InMemorySaver (多轮记忆)
              │     └── Tool: RetrieveLawRegulations
              │                   │
              │                   ▼
              │         RobustRetrievalSkill
              │           ├── 会话级缓存 (FIFO, 10条)
              │           ├── 鲁棒性判断 (空结果/无来源/API失败)
              │           └── HTTP POST → http://127.0.0.1:8800/retrieve
              │
              └── long_term_memory.md → 注入 system_prompt
```

### 6.2 核心组件详解

#### 6.2.1 长期记忆（`long_term_memory.md`）

一份外部 Markdown 文件，定义了 Agent 的行为规则，启动时注入 `system_prompt`：

- **绝对诚实**：只能基于检索工具返回的参考资料回答，严禁编造
- **来源追溯**：每个事实性陈述必须标注出处编号 `[1]`
- **缺资料引导策略**：声明未找到 → 提供一般性引导 → 建议提问方向
- **工具使用纪律**：必须首先调用检索工具；多轮追问优先复用已有资料
- **回答格式规范**：直接答案 → 分点论述 → 引用列表

#### 6.2.2 检索工具（`RobustRetrievalSkill`）

封装了对检索 API 的调用，增加了鲁棒性保障：

```
查询请求
    │
    ├── 检查会话级缓存（归一化后的 query 作为键）
    │     命中 → 直接返回缓存结果（避免多轮追问重复检索）
    │
    ├── 调用检索 API (POST /retrieve)
    │     成功 → 鲁棒性判断:
    │       ├── 有 context + 有 sources → 格式化返回
    │       ├── 空结果或无来源 → 返回 [无相关结果] 提示
    │       └── API 调用失败 → 返回 [检索失败] 提示
    │
    └── 所有调用记录到 events 列表（供 Web 反馈面板展示）
```

**返回格式**（成功时）：
```
【检索到的参考资料】
{context_text}

【可用出处列表】
[1] 来源：《证券投资基金法》 > 第二章 基金管理人，第5-8页
[2] 来源：《私募投资基金监督管理暂行办法》 > 第一章 总则，第25-28页

请严格基于以上参考资料回答，并标注出处编号。
```

#### 6.2.3 LangChain Agent 构建

```python
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=ChatOpenAI(
        model="deepseek-chat",       # DeepSeek 大模型
        temperature=0.0,             # 低幻觉
        max_tokens=1500,
    ),
    tools=[retrieve_law_regulations], # 注册为 LangChain Tool
    system_prompt=SYSTEM_PROMPT,      # 注入长期记忆规则
    checkpointer=InMemorySaver(),    # 按 thread_id 保持多轮对话
)
```

**关键设计**：
- 使用 LangChain 1.x 的 `create_agent`（非老版 `AgentExecutor`），底层为 LangGraph
- 原生 function calling（无文本 ReAct 解析问题）
- `recursion_limit=12` 防无限循环（约 5 次工具往返）

#### 6.2.4 对话流程

```
用户: "私募基金管理人登记需要满足什么条件？"
    │
    ▼  Agent 判断需要检索
    │
    ├── AIMessage (tool_call: RetrieveLawRegulations)
    │     → RobustRetrievalSkill.execute("私募基金管理人登记条件")
    │     → HTTP POST /retrieve
    │     → 返回带出处的参考资料
    │
    ├── ToolMessage (observation: 【检索到的参考资料】...)
    │
    └── AIMessage (最终回答，标注 [1][2] 出处)
```

**多轮追问优化**：
```
用户: "那对注册资本有什么要求？"
    │
    ▼  Agent 检查对话历史中的参考资料是否足够
    │
    ├── 足够 → 直接基于历史资料回答（不调用工具）
    │
    └── 不足 → 再次调用 RetrieveLawRegulations 检索
```

### 6.3 Web 服务层

**`agent_server.py`** 提供 HTTP 接口：

| 接口 | 方法 | 功能 |
|---|---|---|
| `/` | GET | 聊天页面（`static/index.html`） |
| `/health` | GET | 本服务 + 下游检索 API 存活检查 |
| `/chat` | POST | 单轮对话（返回答案 + 工具调用轨迹 + 检索观测数据） |
| `/reset` | POST | 重置会话（新 thread_id） |

**Web 前端**（`static/index.html`）：
- **左侧**：聊天界面，支持多轮对话
- **右侧**：Agent 反馈面板，实时展示：
  - 工具调用（Action）与工具返回（Observation）
  - 检索状态（缓存命中 / 检索成功 / 无结果 / 失败）
  - 耗时统计
  - 历史消息数与缓存条数

## 9. 关键设计决策回顾

| 决策点 | 选择 | 理由 |
|---|---|---|
| 文档提取 | XML 模式（直接解析分页标记） | 零错字、分钟级完成、页码忠实 |
| Token 计数 | tiktoken cl100k_base | 全流程统一，与 GPT-3.5/4 对齐 |
| 切块策略 | 父子块双层结构 | 子块精细检索 + 父块完整上下文 |
| 检索方式 | 向量 + BM25 混合检索 | 语义 + 关键词互补，提升召回率 |
| 精排方案 | 三级降级（云端 → 本地 → 兜底） | 链路永不中断 |
| 上下文组装 | 句子边界窗口扩展 | 截断处永远是完整句子，不破坏语义 |
| Agent 框架 | LangChain 1.x create_agent | 原生 function calling，无文本解析问题 |
| 多轮记忆 | InMemorySaver + thread_id | 轻量、无外部依赖 |
| 检索复用 | 会话级 FIFO 缓存 | 多轮追问避免重复检索，降低延迟 |
