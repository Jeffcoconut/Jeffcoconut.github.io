## part0 总览:

本次项目采用的是非常经典的RAG框架：使用**WordprocessingML**对原生word文档进行解析，然后根据章节等属性做了简单的元数据增强 + 父子块结构（提升检索精准度并保证输出内容完整性）。接着在具体检索层面，采用了传统的**FAISS(dense) + BM25(sparse)**算相似度，归一化后加权融合最终选出k个候选内容块。随后通过**Reranker 大模型**进行精排，并加入**MMR**来保证内容的多样性。最后进行上下文组装，在不超过token预算的前提下添加标记并输出最终文档。

本次项目调用了以下大模型接口：
1. deepseek-v4-flash >( LLM问答 用于DEEP_AGENT部分 )
2. Qwen3-Reranker-4B （Reranker模型）
3. Qwen3-Embedding-4B （Embedding 模型）

## part1 任务描述：

利用DeepAgents + RAG架构，开发基于基金法律条文的智能问答Agent。 Agent在回答过程中应能够写清具体内容来源，严格限制幻觉。在实现具体DEEP——AGENTS问答之前，应先对文档进行切分预处理，提升Agent的问答效率以及内容召回准确率。

## part2 word 切分：

### 2.1 基本思路

>`law_org.docx` 是一本 660 页的《私募基金法律法规汇编》，由几十部法律法规文件拼接而成。本步骤的目标是将其按页码切分为逐页文本。
{: .prompt-info}

~~原本希望跑 MinerU + RAG 这个流程的，但是word文档确实没必要硬使用ocr(太麻烦了)，所以下一个project的时候再开始做~~

如果比较一下这两种**提取模式**：

| 模式 | 适用场景 | 优势 | 劣势 |
|---|---|---|---|
| **xml 模式**（默认推荐） | docx 内含原生文本（非扫描件） | 零错字、分钟级完成、页码更忠实 | 仅限非扫描件 |
| **ocr 模式**（备用） | 扫描件或图片 PDF | 兼容任意格式 | 速度慢、可能有 OCR 错字 |

### 2.2 WordprocessingML

**核心方法**：用 `lxml.iterparse` 流式解析 `document.xml`，按 Word 分页标记切分文本：

```
document.xml
    │
    ├── <w:t> 文本 run               → 累积到当前段落
    ├── <w:tab>                      → 转为制表符
    ├── <w:br type="page"/>          → 硬分页 → 翻页
    ├── <w:lastRenderedPageBreak/>   → 软分页 → 翻页
    ├── <w:tbl>                      → 标记本页 has_table=True
    └── <w:p> 段落结束                → 写入一行
```

**去重规则**：硬分页 *(主动插入分页)*后紧跟的软分页 *（自动分页）*视为同一页界的重复标记，防止页数混乱。

**优势**：
- 页码来自 Word 本身渲染结果，比 LibreOffice 转 PDF 再ocr处理准确性更高
- 流式解析 + `elem.clear()` 及时释放，避免 XML 全量建树的内存峰值

### 2.3 输出格式

```json
// yuchuli/pages_text.json
[
  {
    "page_number": 1,
    "text": "...(该页全部文本)...",
    "has_table": false
  },
  {
    "page_number": 2,
    "text": "...",
    "has_table": true
  }
]
```

## 2. Step 2: 结构识别 + 元数据增强（`structure_metadata.json`）

**脚本**: `yuchuli/step2_structure_metadata.py`

### 2.1 核心目标

将逐页文本进一步解析为**带结构化元数据的段落对象列表**，为后续智能切块提供语境信息。

### 2.2 文档结构分析

经实际勘察，`law_org.docx` 并非单部"编-章-节"式法律，而是由几十部法律法规文件拼接而成：
- 全文出现 **0 次** "第X编"
- 全文出现 **188 次** "第X章"
- 全文出现 **76 次** "第X节"

因此定义的标题层级为：

| 层级 | heading_level | 匹配规则 | 示例 |
|---|---|---|---|
| 一级标题 | 1 | 独占一行的《……》文件标题（可带括注） | `《证券投资基金法》` |
| 二级标题 | 2 | `第X章` | `第二章 基金管理人` |
| 三级标题 | 3 | `第X节` | `第三节 基金托管人` |
| 正文 | 0 | 不匹配以上规则的段落 | 具体法条内容 |

### 2.3 关键规则

**目录页防污染**：第 1 页为目录页，目录行以"制表符+页码数字"结尾（如 `《信托法》\t25`），此类行一律不认定为标题。

**章节栈维护**：
```
遇到一级标题 → 清空栈，压入一级    (新法律文件开始)
遇到二级标题 → 栈截断到一级，压入二级
遇到三级标题 → 栈截断到二级，压入三级
```

每个段落携带的 `section_chain` 就是当前的章节链，例如：
```json
["《证券投资基金法》", "第二章 基金管理人", "第一节 一般规定"]
```

**跨页段落合并**（保守策略）：当上一页最后一段"未以句末标点结尾"（`。！？；：…` 等），且下一页首段不是标题、也不以新条目编号（`第X条`/`（一）`/`一、`/`1.` 等）开头时，判定为同一段落被分页截断，合并之。

**Token 计数**：统一使用 `tiktoken` 的 `cl100k_base` 编码（GPT-3.5/4 所用）。

### 2.4 输出格式

```json
// yuchuli/structure_metadata.json
[
  {
    "para_id": "para_0001",
    "page_start": 1,
    "page_end": 1,
    "section_chain": ["《证券投资基金法》"],
    "heading_level": 1,
    "text": "《证券投资基金法》",
    "token_count": 12,
    "has_table": false
  },
  {
    "para_id": "para_0042",
    "page_start": 5,
    "page_end": 6,
    "section_chain": ["《证券投资基金法》", "第一章 总则"],
    "heading_level": 0,
    "text": "第一条 为了规范证券投资基金活动...(跨页合并后的完整段落)...",
    "token_count": 186,
    "has_table": false
  }
]
```

同时输出 `demo_structure_output.json`，随机抽取 20 个段落（覆盖各层级）供人工检查。

## 3. Step 3: 父子块切分（`chunks.json`）

**脚本**: `yuchuli/step3_chunking.py`

### 3.1 设计理念：Parent-Child Chunking

采用**父子块双层结构**，兼顾检索精度与上下文完整性：

- **父块（Parent）**：800~1200 tokens 的语义完整块，用作上下文窗口
- **子块（Child）**：~250 tokens 的精细块，用作检索单元

```
                    ┌──────────────────────────┐
                    │        父块 parent_0001    │
                    │  (一章或一节的完整内容)      │
                    │                            │
                    │  ┌────────┐ ┌────────┐     │
                    │  │ 子块 1  │ │ 子块 2  │ ... │
                    │  │~250 tok│ │~250 tok│     │
                    │  └────────┘ └────────┘     │
                    └──────────────────────────┘
```

### 3.2 父块构建策略

目标：**800~1200 tokens**，下限 500（`MIN_PARENT_TOKENS`），硬上限 1200（`MAX_PARENT_TOKENS`）。

**切分规则**：

| 规则 | 条件 | 行为 |
|---|---|---|
| 一级标题边界 | `heading_level == 1` 且当前父块非空 | **无条件开新父块**（两部法律绝不混入同一父块） |
| 二级标题边界 | `heading_level == 2` 且当前父块 ≥ 300 tokens | 开新父块（避免碎片） |
| Token 超限 | 当前父块 + 新段落 > 1200 tokens | 先封存再开新 |
| 超长单段 | 单段落本身 > 1200 tokens | 该段落独立成块（不内部拆散，保持语义完整） |

**短父块后处理**（`_merge_short_parents`）：不足 500 tokens 的短父块尝试并入相邻父块（优先向前合并），条件是属于同一法律文件（`section_chain[0]` 相同）且合并后不超 1200 tokens。

### 3.3 子块切分策略

参数：`chunk_size=250 tokens`，`overlap=50 tokens`。

**核心原则**：
- 子块完全包含于父块之内（切分仅在父块内部进行）
- **绝不切断句子**（按句子边界切割）

**算法流程**：

```
父块文本
    │
    ▼  句子切分（。！？；\n 及右引号/括号跟随）
句子序列: [s1, s2, s3, s4, s5, s6, s7, s8, ...]
    │
    ▼  滑动窗口（按句累积，token 接近 250 在最近的句子结束点切断）
窗口1: [s1, s2, s3]        (~250 tokens)
窗口2: [s3, s4, s5, s6]    (overlap: s3 整句回退 ≈ 50 tokens)
窗口3: [s6, s7, s8]        (尾部不足 60 tokens 时并入当前窗口，避免碎片)
```

- **Overlap 实现**：从窗口末尾往回取整句，合计约 50 tokens，保证重叠区也是完整句子
- **尾部吸收**：剩余句子不足 60 tokens 时并入当前窗口，避免碎片子块

### 3.4 输出格式

```json
// yuchuli/chunks.json
{
  "parents": [
    {
      "parent_id": "parent_0001",
      "text": "《证券投资基金法》\n第一章 总则\n第一条 为了规范...",
      "page_start": 1,
      "page_end": 8,
      "section_chain": ["《证券投资基金法》"],
      "token_count": 1056,
      "child_ids": ["child_00001", "child_00002", "child_00003", "child_00004"]
    }
  ],
  "children": [
    {
      "child_id": "child_00001",
      "parent_id": "parent_0001",
      "text": "《证券投资基金法》\n第一章 总则\n第一条 为了规范证券投资基金活动...",
      "page_range": [1, 8],
      "section_chain": ["《证券投资基金法》"],
      "token_count": 248
    }

}
```

**实际规模**：约 **200+ 父块** / **3200+ 子块**（视具体文档内容而定）。

## 4. Step 4: 检索引擎 —— 混合检索、精排、MMR 与上下文组装

**脚本**: `yuchuli/step4_retrieval_engine.py` + `yuchuli/config.py`

### 4.1 流水线全景

```
                          用户查询 (query)
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                       ▼
  ┌──────────┐         ┌──────────┐           ┌────────────┐
  │ FAISS    │         │  BM25    │           │  嵌入后端   │
  │ 向量检索  │         │ 稀疏检索  │           │ (3选1)     │
  │ (余弦)   │         │ (jieba)  │           │            │
  └────┬─────┘         └────┬─────┘           └────────────┘
       │                    │
       ▼                    ▼
  ┌──────────────────────────────┐
  │ ① 混合检索 (hybrid_search)   │
  │   min-max 归一化 + 加权融合    │
  │   final = α·dense + (1-α)·sparse │
  │   → top_k=20 候选             │
  └──────────────┬───────────────┘
                 ▼
  ┌──────────────────────────────┐
  │ ② 精排 (rerank)              │
  │   Cross-Encoder 逐对打分      │
  │   (3级降级: 硅基流动API →     │
  │    本地CrossEncoder →        │
  │    粗排分数兜底)              │
  │   → top3 保底 + threshold 追加 │
  └──────────────┬───────────────┘
                 ▼
  ┌──────────────────────────────┐
  │ ③ MMR 多样性补充              │
  │   mmr = λ·cos(q,c) -         │
  │         (1-λ)·max_cos(c,已选) │
  │   → 额外补充 2 个"相关但不冗余" │
  └──────────────┬───────────────┘
                 ▼
  ┌──────────────────────────────┐
  │ ④ 上下文组装 (assemble_context)│
  │   子块 → 映射回父块            │
  │   按 rerank 权重分配 token 预算 │
  │   句子边界窗口扩展             │
  │   添加来源标记                 │
  │   → context_text (≤3500 tokens)│
  └──────────────────────────────┘
```

### 4.2 嵌入后端（三选一）

通过 `config.EMBEDDING_BACKEND` 配置：

| 后端 | 说明 | 维度 | 特点 |
|---|---|---|---|
| `remote`（默认） | 内网自部署嵌入服务 `192.168.38.122:32001` | 2560 | 服务端已 L2 归一化，~0.8s/条 |
| `local` | sentence-transformers 加载 BGE 模型 | 512 | 本地推理，CPU 友好 |
| `openai` | `text-embedding-3-small` | 1536 | 需 API Key |

**健壮性设计**（remote 后端）：
- 每批 16 条，失败重试 5 次，指数退避 3/6/12/24/48s
- 每 20 批落盘一次检查点（`embeddings_partial.npy`），中断后重跑从断点续传
- 全量 3279 条约需 45 分钟

### 4.3 索引构建与持久化

构建两个索引：

**向量索引（FAISS）**：
```python
# 子块文本 → 嵌入向量 → L2 归一化 → FAISS IndexFlatIP
# 归一化后内积 = 余弦相似度
faiss_index = faiss.IndexFlatIP(dim)   # dim 取决于后端
faiss_index.add(embeddings)            # (N, dim)
```

**BM25 索引**：
```python
# 子块文本 → jieba 搜索引擎模式分词 → BM25Okapi
corpus_tokens = [tokenize_zh(text) for text in child_texts]
bm25 = BM25Okapi(corpus_tokens)
```

**持久化目录** `indices/`：

| 文件 | 内容 |
|---|---|
| `embeddings.npy` | 全量子块嵌入向量 (N, dim) |
| `faiss.index` | FAISS 索引二进制文件 |
| `bm25.pkl` | BM25 索引 pickle |
| `meta.json` | 后端名/模型名/子块数（加载时校验一致性） |

切换嵌入后端/模型后，`meta.json` 一致性校验自动失效，触发重建。

### 4.4 ① 混合检索（`hybrid_search`）

```python
# 稠密路：查询向量与全量子块的余弦相似度（已归一化 → 内积即余弦）
dense = embeddings @ query_vector

# 稀疏路：BM25 打分
sparse = bm25.get_scores(tokenize_zh(query))

# min-max 归一化到 [0,1] + 加权融合
final = alpha * minmax_norm(dense) + (1 - alpha) * minmax_norm(sparse)

# 取 top_k=20 候选
```

默认 `alpha=0.5`，两路权重各半。

### 4.5 ② 精排（`rerank`）

**三级降级后端**：

| 优先级 | 后端 | 模型 | 说明 |
|---|---|---|---|
| 1 | `siliconflow`（默认） | Qwen3-Reranker-4B（云端） | 免本地算力，score 天然 0~1 |
| 2 | `local` | BAAI/bge-reranker-base（本地） | logit 经 sigmoid 归一到 0~1 |
| 3 | 兜底 | 无 | 直接使用粗排融合分数，链路永不中断 |

**选取策略**：
- 按 `rerank_score` 降序，先保底取前 `top_k=3` 个
- 从第 4 名起，分数 ≥ `threshold` 的继续纳入，直到总数达 `max_total=5`

### 4.6 ③ MMR 多样性补充（`mmr_diversify`）

从精排未选中的剩余候选池中，按 MMR（Maximal Marginal Relevance）算法选取 `num_extra=2` 个"相关但不冗余"的补充子块：

```
mmr_score = λ × cos(query, candidate) - (1-λ) × max_cos(candidate, already_selected)
```

`lambda=0.7`：偏向相关性，同时避免选入与已选内容高度重复的片段。

### 4.7 ④ 上下文组装（`assemble_context`）

将最终选中的子块（精排 + MMR）映射回父块，组装为 LLM 可直接消费的上下文：

**步骤**：
1. **分组**：按 `parent_id` 将选中子块归到各自父块
2. **权重分配**：父块权重 = 其下选中子块的 `rerank_score` 之和，按权重比例分配 token 预算（总计 ≤ 3500 tokens）
3. **窗口扩展**：以子块在父块中的位置为中心，按句子为单位向两侧交替扩展，直到逼近该父块的预算；截断处永远是完整句子
4. **来源标记**：每个来源添加 `【来源：章节链，第X-Y页】`
5. **预算控制**：超出总上限时缩窗重试

**输出示例**：
```
【来源：《证券投资基金法》 > 第二章 基金管理人，第5-8页】
第十二条 基金管理人由依法设立的公司或者合伙企业担任。
……（窗口扩展的更多上下文）……

【来源：《私募投资基金监督管理暂行办法》 > 第一章 总则，第25-28页】
第一条 为了规范私募投资基金活动...
```

**返回结构**：
```python
{
    "context_text": "...(带来源标记的完整上下文)...",
    "source_info": [
        {
            "parent_id": "parent_0042",
            "section_chain": ["《证券投资基金法》", "第二章 基金管理人"],
            "page_range": [5, 8],
            "snippet_preview": "第十二条 基金管理人由..."
        }
    ],
    "total_tokens": 3200
}
```

### 4.8 一站式入口（`retrieve`）

`RetrievalEngine.retrieve()` 串联全流程：

```python
engine = RetrievalEngine()
result = engine.retrieve("私募基金管理人登记需要满足什么条件？")
# → 粗排 → 精排 → MMR → 上下文组装 → 返回完整结果
```

**实测性能**（CPU，热状态）：
- 全链路 ~5s：粗排 173ms + 精排 4.5s（硅基流动 API 含网络往返）+ MMR 62ms + 组装 12ms

## 5. 检索 API 服务（FastAPI）

**脚本**: `yuchuli/retrieval_api.py`

### 5.1 服务架构

```
FastAPI 应用 (端口 8800)
    │
    ├── GET  /health          存活检查（含索引规模、嵌入后端信息）
    │
    ├── POST /retrieve        核心检索接口
    │     请求: { query, alpha, coarse_top_k, rerank_top_k, ... }
    │     响应: { context_text, source_info, total_tokens, selected_chunk_ids, timing_ms }
    │
    └── POST /retrieve_and_generate   预留（501，生成环节由 Agent 编排）
```

### 5.2 生命周期

应用启动时通过 `lifespan` 上下文管理器初始化 `RetrievalEngine`：
- 磁盘有索引（`indices/`）→ 秒级加载
- 无索引或配置不一致 → 自动构建并持久化

```bash
curl http://127.0.0.1:8800/retrieve \

```

{

## 6. DeepAgent 问答框架接入

### 6.1 整体架构

```
用户 ←→ Web 对话界面 (index.html)
              │
              ▼
         agent_server.py (FastAPI, 端口 8900)
              │
              │  POST /chat { message, thread_id }
              ▼
         deepagent_app.py (Agent 核心)
              │
              ├── LangChain create_agent
              │     ├── LLM: ChatOpenAI (DeepSeek)
              │     ├── Checkpointer: InMemorySaver (多轮记忆)
              │     └── Tool: RetrieveLawRegulations
              │                   │
              │                   ▼
              │         RobustRetrievalSkill
              │           ├── 会话级缓存 (FIFO, 10条)
              │           ├── 鲁棒性判断 (空结果/无来源/API失败)
              │           └── HTTP POST → http://127.0.0.1:8800/retrieve
              │
              └── long_term_memory.md → 注入 system_prompt
```

### 6.2 核心组件详解

#### 6.2.1 长期记忆（`long_term_memory.md`）

一份外部 Markdown 文件，定义了 Agent 的行为规则，启动时注入 `system_prompt`：

- **绝对诚实**：只能基于检索工具返回的参考资料回答，严禁编造
- **来源追溯**：每个事实性陈述必须标注出处编号 `[1]`
- **缺资料引导策略**：声明未找到 → 提供一般性引导 → 建议提问方向
- **工具使用纪律**：必须首先调用检索工具；多轮追问优先复用已有资料
- **回答格式规范**：直接答案 → 分点论述 → 引用列表

#### 6.2.2 检索工具（`RobustRetrievalSkill`）

封装了对检索 API 的调用，增加了鲁棒性保障：

```
查询请求
    │
    ├── 检查会话级缓存（归一化后的 query 作为键）
    │     命中 → 直接返回缓存结果（避免多轮追问重复检索）
    │
    ├── 调用检索 API (POST /retrieve)
    │     成功 → 鲁棒性判断:
    │       ├── 有 context + 有 sources → 格式化返回
    │       ├── 空结果或无来源 → 返回 [无相关结果] 提示
    │       └── API 调用失败 → 返回 [检索失败] 提示
    │
    └── 所有调用记录到 events 列表（供 Web 反馈面板展示）
```

**返回格式**（成功时）：
```
【检索到的参考资料】
{context_text}

【可用出处列表】
[1] 来源：《证券投资基金法》 > 第二章 基金管理人，第5-8页
[2] 来源：《私募投资基金监督管理暂行办法》 > 第一章 总则，第25-28页

请严格基于以上参考资料回答，并标注出处编号。
```

#### 6.2.3 LangChain Agent 构建

```python
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=ChatOpenAI(
        model="deepseek-chat",       # DeepSeek 大模型
        temperature=0.0,             # 低幻觉
        max_tokens=1500,
    ),
    tools=[retrieve_law_regulations], # 注册为 LangChain Tool
    system_prompt=SYSTEM_PROMPT,      # 注入长期记忆规则
    checkpointer=InMemorySaver(),    # 按 thread_id 保持多轮对话
)
```

**关键设计**：
- 使用 LangChain 1.x 的 `create_agent`（非老版 `AgentExecutor`），底层为 LangGraph
- 原生 function calling（无文本 ReAct 解析问题）
- `recursion_limit=12` 防无限循环（约 5 次工具往返）

#### 6.2.4 对话流程

```
用户: "私募基金管理人登记需要满足什么条件？"
    │
    ▼  Agent 判断需要检索
    │
    ├── AIMessage (tool_call: RetrieveLawRegulations)
    │     → RobustRetrievalSkill.execute("私募基金管理人登记条件")
    │     → HTTP POST /retrieve
    │     → 返回带出处的参考资料
    │
    ├── ToolMessage (observation: 【检索到的参考资料】...)
    │
    └── AIMessage (最终回答，标注 [1][2] 出处)
```

**多轮追问优化**：
```
用户: "那对注册资本有什么要求？"
    │
    ▼  Agent 检查对话历史中的参考资料是否足够
    │
    ├── 足够 → 直接基于历史资料回答（不调用工具）
    │
    └── 不足 → 再次调用 RetrieveLawRegulations 检索
```

### 6.3 Web 服务层

**`agent_server.py`** 提供 HTTP 接口：

| 接口 | 方法 | 功能 |
|---|---|---|
| `/` | GET | 聊天页面（`static/index.html`） |
| `/health` | GET | 本服务 + 下游检索 API 存活检查 |
| `/chat` | POST | 单轮对话（返回答案 + 工具调用轨迹 + 检索观测数据） |
| `/reset` | POST | 重置会话（新 thread_id） |

**Web 前端**（`static/index.html`）：
- **左侧**：聊天界面，支持多轮对话
- **右侧**：Agent 反馈面板，实时展示：
  - 工具调用（Action）与工具返回（Observation）
  - 检索状态（缓存命中 / 检索成功 / 无结果 / 失败）
  - 耗时统计
  - 历史消息数与缓存条数

## 9. 关键设计决策回顾

| 决策点 | 选择 | 理由 |
|---|---|---|
| 文档提取 | XML 模式（直接解析分页标记） | 零错字、分钟级完成、页码忠实 |
| Token 计数 | tiktoken cl100k_base | 全流程统一，与 GPT-3.5/4 对齐 |
| 切块策略 | 父子块双层结构 | 子块精细检索 + 父块完整上下文 |
| 检索方式 | 向量 + BM25 混合检索 | 语义 + 关键词互补，提升召回率 |
| 精排方案 | 三级降级（云端 → 本地 → 兜底） | 链路永不中断 |
| 上下文组装 | 句子边界窗口扩展 | 截断处永远是完整句子，不破坏语义 |
| Agent 框架 | LangChain 1.x create_agent | 原生 function calling，无文本解析问题 |
| 多轮记忆 | InMemorySaver + thread_id | 轻量、无外部依赖 |
| 检索复用 | 会话级 FIFO 缓存 | 多轮追问避免重复检索，降低延迟 |
